So naturally, in the next 24h, I secured a used Whoop off facebook marketplace to try it out. ### Connection
Jude describes this in great detail (link: https://judes.club/writing/cracking-the-whoop-5-bluetooth-protocol/#a-quick-bluetooth-primer text: here) but in a nutshell, we need to "bond" (basically, pairing or authentication) Whoop and mobile device. After struggling for a while, I learned that you need to pair through the official Whoop app for it to actually "bond" and have the conenction persist at the system level. Whoop understandably has a proprietary command to do that. 

(image: img_7377-portrait.png caption: Thanks, Matthew class:th-image)

Now that we have system level connection, next step is to have our app persist the connection (or re-connection) in all scenarios; foreground, background, and app closure. 

#### Foreground
Foreground is comparatively easy. In our app, we use Apple’s (link: https://developer.apple.com/documentation/corebluetooth/cbcentralmanager text: CoreBluetooth framework) to create a Bluetooth central session. Our “scan” functionality then looks for Whoop-specific UUIDs and connects to the matching device. After a successful connection, the app remembers connected devices' UUID, so on the next app open, it can reconnect automatically without requiring another manual scan.

#### Background
When you put an app in the background, iOS usually suspends the process. It remains in memory but gets little to no CPU time. Luckily, iOS (link: https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html text: allows) apps to declare certain background capabilities, including BLE-related work through bluetooth-central. 

With that enabled, CoreBluetooth can keep managing relevant BLE activity on the app’s behalf and briefly wake the app when Bluetooth events occur, such as a subscribed characteristic receiving new data, a connection succeeding, or a connection dropping. However, now that creates another problem of battery drainage on both phone and Whoop. We'll discuss it more later.

#### App Closure and Re-open
When app is closed, app looses connection to Whoop and auth is lost. On reconnection, as noted earlier, it automatically recognizes device, connects, and authenticates.

### Getting data
There are couple things we need to understand first before asking Whoop for the data it collects. I am going to explain each of those briefly, feel free to skip if you are familiar with the concept.

#### Bits, bytes, and Nibbles
When working with Bluetooth data, it helps to remember that devices ultimately send bytes. A byte is eight bits and can represent values from 0 to 255. Engineers often display bytes in hexadecimal because it is more compact than binary, with every two hex digits representing exactly one byte. For example, the value 75 can be written as:
- `75` in decimal
- `0x4B` in hexadecimal or
- `01001011` in binary 

The underlying value is identical. The key distinction is that some hexadecimal values represent measurements, such as heart rate or battery percentage, while others are simply identifiers. For example, `0x4B` may decode to a heart rate of 75 bpm, whereas `0x2A37` is a Bluetooth characteristic UUID that serves as a name rather than a value. 

Once you understand that BLE packets are just sequences of bytes and that hexadecimal is simply a human-friendly way to view them, decoding sensor data becomes much less intimidating.

#### The Envelope
Now that we understand what data may look like, let's understand how to format our request to the device it in a way it is expecting, so in turn, it can give us the data we need.

Every BLE packet (a request or a response) is wrapped in an envelope. Think of it as a shipping box around the actual message. The envelope contains metadata such as packet length, version, sequence numbers, and checksums that help the receiver understand and validate the data.

The envelope matters because devices expect it to be constructed exactly right. If the length, checksum, or control fields are incorrect, the packet may be rejected or ignored entirely.

Jude explains this really well in (link: https://judes.club/writing/cracking-the-whoop-5-bluetooth-protocol/#the-envelope text: his article), so I am not going to re-invent the wheel, but this is what an envelope looks like:

(image: whoop5-frame-1.jpg class:th-image caption: The Envelope ([Source](https://judes.club/writing/cracking-the-whoop-5-bluetooth-protocol/#the-envelope)))

For example, a WHOOP packet might look something like:

```
┌──────────────────────────── Outer Envelope ─────────────────────────────┐
[0xAA][0x01][0x0012][0x0001][CRC16][0x23][0x05][0x91][0x01][payload][CRC32]
                                   └──────── Inner Message ────────┘
```

where:

```
[0xAA]       Start of frame ("a packet begins here")
[0x01]       Protocol version
[0x0012]     Packet length
[0x0001]     Control field
[crc16]      Header integrity check (of bytes 0..6)

[0x23]       Message type (COMMAND)
[0x05]       Sequence number
[0x91]       Command (GET_HELLO)
[0x01]       Command-specific flag
[payload]    Actual command data

[crc32]      Payload integrity check (of inner)
```

You can think of the first five fields as the shipping label and packaging instructions, while the inner fields contain the actual message. In this example, the message is `GET_HELLO`, packet number `5`, with any additional data stored in the payload. Before Whoop processes the command, it first verifies the length and checksums to ensure the packet arrived intact.
